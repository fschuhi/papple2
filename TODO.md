## Cross reference

- What it is for (2026-10-11): which data each instruction reads and writes, from one run. Questions it should answer: which tables a routine reads from or writes to; who uses `(zp),Y`, on which ranges; which routines modify their own or other routines' code; for self-modification with indexed reads and writes, where those ranges live. Easier to explain than the tiling or the stack tracking, and good for maps and heat maps.
- Counts, not a trace (decided 2026-10-11): one row per instruction, kind of access and address, with a count, as `Tiling` counts its tiles. The questions above are about where, not when. A trace (every access in order, with its `instruction_count`) waits until a question needs the order; see the scratchpad item on "profile" and "trace".
- What is watched: all reads and all writes of data (`after_read_data`, `after_write_data`), and the pointer reads of the indirect modes (`after_read_pointer`). One instruction can give several rows: `LDA ($06),Y` reads `$06` and `$07` as the pointer, then the byte at pointer + Y as data; `INC abs` reads and writes. Zero page counts like any other address. _Open:_ whether stack accesses (`after_read_stack`, `after_write_stack`) belong in it.
- Per access: the instruction's address (`cpu.last_PC`, valid during a memory hook), its addressing mode (from the opcode, through the disassembler's table), read or write, the effective address, and for `(zp),Y` and `(zp,X)` the zero-page pointer.
- Shape: like the tiling. An experiment runs once, perhaps slower than the others, and writes CSV files; analyses at the prompt read them and join them with the run's routines. A map like `lr_count.py`'s (read as data, written, written where code ran) comes cheaply from the same files.
- _Open before building:_ the CSV's columns; whether the ranges an instruction touches are written or computed at the prompt; the experiment's name.
