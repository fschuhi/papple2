TRY_MOVING_LEFT Inside MOVE_PLAYER

Xekri marks TRY_MOVING_LEFT as a subroutine of its own. papple2 puts it inside MOVE_PLAYER. This page explains why the run can't tell them apart, what rule could, and what that rule risks.

The case

MOVE_PLAYER ends with a dispatch: for "move left" it jumps to TRY_MOVING_LEFT, and otherwise it returns. TRY_MOVING_LEFT lies right behind MOVE_PLAYER's last RTS.

Why it is tricky

  • One way in. No JSR calls TRY_MOVING_LEFT. The only way in is the JMP at 65c8. For the run, that is a tail call: Doug jumps instead of calling, and TRY_MOVING_LEFT's own exit returns to MOVE_PLAYER's caller.
  • Forward, inside the range. The jump goes forward, a few bytes, and no routine starts in between. To the run this looks like any jump inside one routine, e.g. over an if branch.
  • None of today's rules fires. The shared-code rules, Rule A included, need two ways in from two routines. The orphan rule needs code no routine holds. Here there is one way in, and MOVE_PLAYER holds the code.

The signal, part 7 of the rule on paper

One thing gives it away: the block right in front of the target, 65d2, ends with MOVE_PLAYER's own RTS. So nothing can run on into 65d3, and a jump is the only way to get there.

Part 7 says: a JMP target that lies right behind a block ending in RTS starts a routine of its own. The rule was graded on paper on 2026-10-17. It finds TRY_MOVING_LEFT, and in this run that is the only case it finds.

What "risk" means

The risk is a false split: part 7 would cut a routine in two where the author wrote one subroutine. That happens when the same shape appears inside one subroutine. A common 6502 pattern has it: the exit placed in front of the loop, so the loop's test can branch back to it.

An invented example, not from Lode Runner
FIND_END LDX #0one subroutine
+-- JMP .loopinto the loop
|.exit RTSthe exit, placed in front
+->.loop LDA table,Xright behind an RTS, reached only by JMP: part 7 would cut here
BEQ .exit
INX
JMP .loopback to the loop head

FIND_END would become two routines: two instructions, and a loop with no entry of its own. Nothing like this ran in the attract play, so the grade can't show the risk. A routine that is cut in two is harder to read than one that is too big, and a wrong split is the harder mistake to spot.

Would more movements help?

Yes, you are right: in this run the player only moves left and digs left. TRY_MOVING_RIGHT, _UP and _DOWN never ran.

A run with all four movements would not resolve the case by itself. MOVE_PLAYER presumably reaches the other three the same way, by a JMP forward from its dispatch. Then today's rules would put all four movements inside MOVE_PLAYER, not just one.

But such a run is exactly what the rule needs to be tested:

  • A second case of the same shape. That is the hold-out that is missing today: a rule built on one case and graded on the same case proves little.
  • A test of the signal itself. TRY_MOVING_RIGHT lies right behind TRY_MOVING_LEFT's JMP DRAW_PLAYER, not behind an RTS. Part 7 as written would miss it. The signal is probably "behind a block that can't run on": an RTS or a JMP. A fuller run would show whether that is right.
  • More code for the risk to show up in. If part 7 cuts something wrongly, more code that ran gives it more chances to do so where we can see it.

So: park group B until there is a run in which the player moves in all four directions, then decide part 7 on four cases instead of one.
